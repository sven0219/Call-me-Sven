# 华为 FTTR 主从网关之间投屏失败：从 ARP 抓包到 IPv6 防火墙对照

家里的 Mac 和小米电视连接同一个 Wi-Fi 名称，却一度无法投屏。FTTR 由华为 V175 主网关和 K155 从网关组成；后来确认，Mac 连接 K155 时曾无法访问电视，而连接 V175 时可以访问。本文记录实际测到的现象、如何确认两台设备的接入节点，以及一次与 IPv6 防火墙开关有关、**仍未完成严格复验**的对照。

## 网络拓扑与容易误判的地方

| 设备 | 地址 | 确认接入节点的方法 |
|---|---|---|
| 主网关 V175 | `192.168.1.1` | 5 GHz BSSID `f0:c4:78:d6:2c:d8` |
| 从网关 K155 | `192.168.1.13` | 5 GHz BSSID `c8:84:cf:16:92:54` |
| 小米电视 | `192.168.1.8` | ADB 读取实时 Wi-Fi BSSID |
| Mac | `192.168.1.156` | macOS Wi-Fi 详情中的 BSSID |
| Mac mini | `192.168.1.160` | 用户确认连接 K155，用于辅助测试与抓包 |

主从网关共用 SSID，**默认网关都是 `192.168.1.1`**，不能用默认网关判断 Mac 连接了哪个节点。主网关设备列表中的 `SSID5`、`ONU1` 是接口标记，也不能单凭它们确定电视究竟连接哪台网关。Wi-Fi 终端还可能自动漫游，因此每轮测试最好同时记录 BSSID。

## 第一轮：为什么怀疑局域网转发

Mac 连接 K155（BSSID `c8:84:cf:16:92:54`）时，两台网关的管理 IP 都能 ping 通，唯独电视 `192.168.1.8` 无法 ping 通；TCP `47000` 连接超时，电视的 ARP 记录显示 `incomplete`。Mac 连接 V175 时，曾能 ping 通电视、发现 AirPlay 服务，并连接 `192.168.1.8:47000`。K155 的 FTTR 链路在主网关页面显示在线、配置已同步；重启 K155 后也曾再次观察到故障。

在同样连接 K155 的 Mac mini 上抓包，发送 `ping` 时看到了连续的请求：

```text
Request who-has 192.168.1.8 tell 192.168.1.160
Request who-has 192.168.1.8 tell 192.168.1.160
```

没有看到 ARP 应答。这说明当时 Mac mini 发出了询问电视 MAC 地址的广播，却没收到答复；**单侧抓包不能区分**请求没到电视、电视没有响应，还是响应没返回。由于连 IPv4 邻居地址都无法解析，当时的问题不只是 AirPlay 服务发现或某个投屏端口。

复现时可在 Mac mini 的 `en1` 上抓包，在另一个终端 ping 电视：

```bash
sudo tcpdump -i en1 -n -e -l 'arp and host 192.168.1.8'
ping -c 4 192.168.1.8
```

两台网关的 SSH 22 端口测试均超时；拿到的网页管理密码能登录主网关，却不能登录从网关，因此没有在网关上读取转发规则。

## 验证电视和 Mac 是否真的连接不同节点

后来电视可达时，通过 ADB 连接到电视（需电视已经开放并授权网络调试）：

```bash
adb connect 192.168.1.8:5555
adb -s 192.168.1.8:5555 shell cmd wifi status
```

实时状态显示电视 IP 为 `192.168.1.8`，BSSID 为 **`f0:c4:78:d6:2c:d8`（V175）**；同期 Mac 的 Wi-Fi 截图显示 **`c8:84:cf:16:92:54`（K155）**。这才证实那次测试确实是跨 FTTR 节点通信，而不只是两个设备碰巧用了同一 SSID。电视和 Mac 都可能漫游，这个结论只针对记录状态的时刻。

## IPv6 防火墙开关的对照

看到一篇[华为 FTTR 实战文章](https://blog.csdn.net/weixin_32932149/article/details/167112271)提到，部分固件中的主网关 IPv6 防火墙设置可能影响 LAN 设备互访，于是在 V175 的 **高级配置 → 安全设置 → IPv6 防火墙** 页面检查了「**使能IPv6防火墙控制转发报文**」。

目前记录下来的顺序是：

1. **关闭该选项后**，用户反馈问题解决。一次 Mac 连接 K155 的复测中，电视 ping 4/4 成功、ARP 解析到电视 MAC、TCP `47000` 可连接，`_airplay._tcp.local` 也发现了电视；Mac mini 当时同样可 ping 通电视。
2. 为验证关联，用户**主动重新开启**该选项。Mac 再次确认连接 K155 后，电视 ping 0/4、TCP `47000` 报 `Host is down`，ARP 为 `incomplete`；两台网关仍可达。
3. 随后 Mac 再次连接 K155 时，复测电视 ping 4/4 成功、ARP 和 TCP `47000` 均正常；ADB 同时确认电视连 V175。**这次恢复时没有同步记录防火墙开关状态**，所以不能把它直接算作“再次关闭后恢复”。实际屏幕镜像的最终结果也没有同步留证。

这些观察提示该开关与故障**可能高度相关**，但不是已确认的修复机理：标准 IPv6 防火墙通常不应直接过滤 IPv4 ARP，具体固件内部行为未知。不能仅凭时间接近，就断言它直接拦截了 ARP；也不应把单次恢复当作稳定修复。

## 补充：扫描设备列表不能代替故障定位

另一次从 Mac 对主网关截图中的 IPv4 地址逐一做两次 ping 和 ARP 检查，`192.168.1.8`、`.13`、`.21`、`.22`、`.26`、`.28`、`.32`、`.84`、`.98`、`.129`、`.142`、`.160`、`.169`、`.170` 能 ping 通；`.14`、`.20`、`.24`、`.27`、`.128`、`.130` 未收到 ping 回应且 ARP 为 `incomplete`；`.91` 不回应 ping 但有 ARP 记录。`.156` 是测试 Mac 自身，不能作为远端设备统计。

该轮没有同步记录 Mac 的实时 BSSID 和防火墙状态。网关页面写“在线”也不保证终端在几秒内响应 ARP/ICMP；设备休眠或限制 ping 都可能影响结果，不能把所有无回应地址直接归因于 FTTR 隔离。

## 后续如何做可重复验证

保持电视在线、IP 为 `192.168.1.8`，并用 `cmd wifi status` 核实其 BSSID；保持 Mac 在 K155，测试前后核对 BSSID。每次**只改变一个设置**，记录开关状态、应用时间，以及以下结果：

```bash
ping -c 4 192.168.1.8
arp -n 192.168.1.8
nc -G 3 -zv 192.168.1.8 47000
```

最后实际尝试屏幕镜像。如果在相同接入节点和电视在线的条件下，多次稳定出现「开时 ARP 失败、关时 ARP 成功」，就有更强证据请联通检查主网关固件的转发实现和更精确的局域网规则。关闭该选项可能改变 IPv6 转发流量的防护，长期使用前应确认其影响范围。
