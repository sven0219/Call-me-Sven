# 华为 FTTR 主从网关投屏失败排查：ARP 与 IPv6 防火墙

## 1. 现象

这次排查始于想通过 ADB 调试小米电视（`192.168.1.8`），却发现 Mac（`192.168.1.156`）一直连不上电视。这让我想起此前投屏也时好时坏，于是决定把网络连通问题查清楚。家里的华为 FTTR 由 V175 主网关（`192.168.1.1`）和 K155 从网关（`192.168.1.13`）组成；排查中发现 Mac 连接从网关时曾无法访问电视，而连接主网关时电视可达、AirPlay 服务也能发现。

主从网关使用同一个 Wi-Fi 名称，设备的默认网关都显示 `192.168.1.1`。因此不能靠 SSID 或默认网关判断接入节点，要看 **BSSID**：V175 的 5 GHz BSSID 为 `f0:c4:78:d6:2c:d8`，K155 的为 `c8:84:cf:16:92:54`。

## 2. 排查过程

1. **确认不是整个从网关断网。** Mac 的 BSSID 显示连接 K155 时，可以访问 `192.168.1.1` 和 `192.168.1.13`，但 ping 电视 `192.168.1.8` 为 0/4，连接 TCP `47000` 超时，`arp -n 192.168.1.8` 显示 `incomplete`。主网关管理页显示 K155 在线、FTTR 链路正常；重启 K155 后故障仍曾出现。

2. **抓包定位到 ARP 阶段。** 另一台连接 K155 的 Mac mini（`192.168.1.160`）也无法访问电视。在它的 `en1` 接口上运行 `sudo tcpdump -i en1 -n -e -l 'arp and host 192.168.1.8'`，同时 ping 电视，看到重复的 `Request who-has 192.168.1.8 tell 192.168.1.160`，没有收到 ARP 应答。这说明当时 Mac mini 发出了查询电视地址的请求，却没有得到回应；单侧抓包无法判断请求是否到达电视，或回应是否在返回途中丢失。问题不只在投屏应用或服务发现。

3. **核实电视与 Mac 的接入节点。** 后来电视可访问时，用 `adb connect 192.168.1.8:5555` 和 `adb -s 192.168.1.8:5555 shell cmd wifi status` 读取电视实时 Wi-Fi 状态：电视 BSSID 为 `f0:c4:78:d6:2c:d8`，即 V175；同期 Mac 的 Wi-Fi 截图显示 `c8:84:cf:16:92:54`，即 K155。确认这次测试确实是跨节点通信。设备可能漫游，所以这个结论只对应当时的状态。

4. **对照 IPv6 防火墙设置。** 参考一篇[华为 FTTR 排查文章](https://blog.csdn.net/weixin_32932149/article/details/167112271)的提示，检查 V175「高级配置 → 安全设置 → IPv6 防火墙」中的「使能IPv6防火墙控制转发报文」。关闭该选项后，用户反馈问题解决；Mac 在 K155 下复测电视 ping 4/4、ARP 正常、TCP `47000` 可连接，AirPlay 服务也能发现。随后用户主动重新开启该选项做对照：Mac 仍连接 K155 时，电视又 ping 0/4、ARP 为 `incomplete`、TCP `47000` 报 `Host is down`，但两台网关仍可访问。再后来 Mac 连接 K155 时电视再次可达，不过**这次恢复没有同步记录防火墙开关状态**，不能据此写成严格完成了「关 → 开 → 关」复验。

## 3. 结论

已确认：故障发生时，从网关侧设备连电视的 IPv4 ARP 都无法解析；Mac 连 K155、电视连 V175 的跨节点场景曾经验证可通。IPv6 防火墙选项**关闭时可达、重新开启后不可达**的观察，与故障高度相关，是目前最有价值的排查线索。

但具体根因尚未确认：正常的 IPv6 防火墙不应直接过滤 IPv4 ARP；既没有网关内部规则，也没有在同一节点状态下完整记录再次关闭后的开关状态和实际屏幕镜像结果。因此不能断言该选项直接拦截 ARP，或保证关闭后永久修复。若需进一步确认，应保持电视在线、Mac 固定连接 K155，记录每次开关状态及 BSSID，再对照 ping、ARP 和实际投屏结果。
